# 分层交接协议（可移植契约）

> 本文是设计原理，不含任何项目事实。可整段贴进项目 `AGENTS.md` 的附录，或给新协作者读。
> 配套工具见 `handoff-kb` skill 的 `scripts/`。

## 1. 问题定义：上下文爆炸是算术问题

假设一个项目有 N 份文档、总体积 S 字节，新会话接手时全读：

```
接手成本 = S / 4.5  （中文 UTF-8，约 4.5 B/token）
```

当 S = 221 KB 时就是 ≈49k tokens，一上来烧掉三分之一以上上下文。而**真正决定接手质量的信息**（现在在干嘛、下一手、别做什么）通常不到 20 KB。

结论：**不要压缩总量，要压缩「必读集合」**。把全库按「读取频率」分层，让必读集合恒定在 `入口 + 现状 + 基线` 三份以内。

实测（某路由器项目）：全库 1,759 行 / 221 KB，改造后接手只读 `05`(7.7 KB) + `00`(13 KB) = 20.6 KB ≈ 4.5k tokens，**降 90%**；同期总行数反而增加，因为过程被归档而非删除。

> 这套结构本质是「**人工 RAG + 分层 wiki**」：用文件名、章节号、ID 编号做人工路由，没有 embedding / chunking / 语义 recall。优点是零依赖、纯文本、可 diff、agent 不用任何工具就能读；缺点是**规模上限必须靠机制守**，不靠人记得住。

## 2. LAYER 模型

| 层 | 文件 | 写什么 | 读频率 | 变更方式 |
|---|---|---|---|---|
| L0 入口 | `AGENTS.md` + `CLAUDE.md`/`GEMINI.md` 指针 | 接手顺序、写回规则、硬约束、文件分工。**绝不写当前值** | 每次 | 极少改 |
| L1 事实 | `00` 唯一共享页 + `01`–`0N` 分册 | 当前值 / 不变量 / 判据 / 命令 / 坑与结论 | 按线 | 少改，只写当前值 |
| L2 现状 | `05_进度仪表盘.md` | 各线状态、待办、交叉点、接手顺序、最近 5 条摘要 | **每次必读** | 常改且短 |
| L3 流水 | `06_会话日志.md`（历史卷）+ `06_流水/<线>.md`（按线分片） | append-only 时间线，>3 行的完整记录 | 追溯才读 | 按线只写自己那份，不改别人的行 |
| L4 归档 | `90_过程档案.md` + `归档/` | 过程证据 / 验证快照 / 版本考古 / 已消除矛盾 / 一次性任务单 | 几乎不读 | 折叠时写 |

**L1 按「线」还是按「领域」切**：项目有多条并行推进线（固件 / 运行态 / 服务端 / 测速）就按线切；单一复杂领域（游戏数据 / mod / 流程）就按领域切。两种都对，关键是**一条线只归属一份分册**，别让一份事实在两处出现。

**L0 的唯一性**：`AGENTS.md` 是唯一权威入口，`CLAUDE.md`/`GEMINI.md` 各两行指针（有些客户端不认 AGENTS.md）。三者是入口不是第 N+1 份事实文档——一旦往里填当前值，立刻出现第二套说法。

## 3. 编号契约

- `00` 基线表用 `K-xx`、结论索引用 `G-xxx`：每行带 **状态列**（`有效` / `待核` / `已作废 → K-xx`）。
- 引用别处事实只写 ID，不复述数值：`见 00 K-07`、`详见 90 §D.4`。
- **作废行连同 ID 一起保留，ID 永不复用**；被取代的条目互相指。
- 事实层的 `§1–§9`、归档的 `§A–§G` 是跨文档契约：改内容可以，**别重排编号**。
- 好处：答完一个问题可以直接给 ID，对方不必翻分册；改一个值只需动一处。

## 4. 并发模型：靠 git，不靠纪律

多个会话同时改共享文档，失效模式按严重度：

1. **覆盖**（最致命）：`05` 共享可写，两个会话「读-改-写」后写者全胜。无 git 就没有 diff / 回滚 / 冲突提示，唯一的冲突信号是首行时间戳，靠人眼。
2. **文档与实机漂移**：文档是快照，实机是真值。需要**只读自检脚本**（`scripts/handoff-check.sh` 一类）定期核对，脚本只 echo 不改任何东西。
3. **流水无限增长**：`06` 按每天 2–3 条、每条 400 字，一个月就到 ~2,000 行 / 100 KB，变成第二个归档。
4. **半自动失同步**：`05` 的更新仍靠会话记得写，漏写就静默失同步。

对应的机制（按杠杆排序）：

| 机制 | 解决 |
|---|---|
| **`git init` + 收尾必 commit** | 1（并顺带给出别人的改动可见性） |
| **`06` 按线分片（一写者一文件）** | 1 的更强解：从根上不共享单文件，借鉴 `pmikutel/directed-memory-bank`；历史卷保留只读 |
| `.gitignore` 排凭证 / 日志 / 大二进制 + 除密扫描 | 凭证进历史、仓库爆体积 |
| `06` 轮转阈值（**单分片** 200 行 / 60 KB → 折叠进 `90`） | 3 |
| `05` §5 写死阈值与「改前 status / 改后 diff」 | 3 + 4 |
| 只读自检脚本 | 2 |
| 每次自检自动在 `05` 追加时间戳 | 4（锦上添花） |

现场证据：某次 `git add` 时发现另一个会话刚新建了一份临时脚本——**没有 git 时这种并发完全不可见**。另一次 `git status` 抓到两个会话写了 `05`/`06` 但都没提交，正好避免了互相覆盖。

**`.gitignore` 必须先写再 add**，尤其视频 / 大二进制：进了历史就再也删不掉。除密扫描正则至少覆盖 `LTAI...`、私钥 PEM、`password|secret|token = '...'`、`sk-...`。成品交付物（xlsx 等）要进库以便回滚，但 diff 看不出内容 → 在 commit message 里写版本号 + SHA256。

## 5. 阈值表

| 对象 | 阈值 | 动作 |
|---|---|---|
| `05` §0 现状 | > 4 行 | 压缩，细节进 `06` |
| `05` §6 摘要 | > 5 条 / 单条 > 3 行 | 整条移进 `06` |
| `06` 流水 | > 200 行 或 > 60 KB | 按主题折叠进 `90 §X`，`06` 只留标题 + 指针 |
| `00` 基线 | > 150 行 | 升级成结论索引（K-xx + 状态列） |
| `90` 归档 | > 600 行 | 再分卷或移 `归档/` |
| 事实层分册 | > 8 个 | 按领域合并 |

**触线才动手**：进度文件只有 30 行时拆成两份，反而要翻两份。某项目是涨到 79 行 / 17 KB、单条 976 字才拆的。

## 6. 反模式（真实案例）

| 坑 | 后果 |
|---|---|
| 长话术三份同源（`00` §6 / `04` §9 / 启动 txt） | 改一处漏两处，口径漂移 |
| 500 行参考手册列进「接手必读」 | 每个新会话白烧大量 token |
| `05` 堆已完成的待办 | 待办区被历史稀释，看不到下一手 |
| 删过程时连「踩过的坑与结论」一起删 | 下次重走旧路 |
| 明文密码 / AK 直接进 git | 凭证永久进历史，删不掉 |
| 无 git 时并发改共享文档 | 后写者全胜且无提示 |
| 提前拆分小文件 | 接手要翻两份 |
| 重排 §编号 / 复用 K-xx ID | 全库引用失效 |
| 整文件覆盖写 `05` | 抹掉别的会话刚追加的行 |

清理原则一句话：**只删「已结案背景 / 过程性时间戳 / 验证快照」，保留「当前基线 / 配置 / 踩过的坑 / 结论 / 命令参考」**；删掉的过程不丢，整段归档到 `90`，主文档留 `详见 90 §X`。

## 7. 从零搭建 / 存量迁移

从零：`kb-init.py --target DIR --project NAME --lines "线A,线B,线C"` → 填基线 / 现状 / 硬约束 → 补 `.gitignore` 与自检脚本。

存量五步（**别跳步**）：
1. `git init`（先 `.gitignore` 再 add）——没有版本控制，后面任何拆分都无法回滚。
2. 过程下沉到 `90`，主文档留指针。
3. 建 `05`，把散落的状态 / 待办抽到一处，删同源副本。
4. 单条 >3 行或 `05` 涨到 ~70 行时拆 `06`；搬运用 `sed -n 'Np' >> 06` + `cmp` 校验，别手抄。
5. 加机制：`AGENTS.md` 入口、K-xx 编号与状态列、`06` 阈值、commit 规则。

> 逐步展开的目标 / 判据 / 命令 / 产物 / 坑见 `migration.md`；给新会话开改造任务直接贴 `assets/migration-prompt.txt`。

## 8. 验收四问

改造完只给新会话看 `05` 一份，答得出即合格：

1. 各条线现在什么状态？
2. 下一手做什么？
3. 哪些待定 / 进行中 / 已完成？
4. 动某个具体配置该读哪几份？

答不出 = `05` 缺信息或又膨胀了，**不要靠全读全库去补**。

## 9. 规模上限与演进信号

这套结构没有语义检索，靠人工路由，因此有天花板。出现下列信号就该升级（而不是继续加文档）：

- 需要「问一句话命中段落」而不是「知道去哪份翻」 → 引入 embedding / 语义检索层。
- `00` 超过 150 行且 K-xx 超过 30 条 → 结论索引独立成册。
- 并发会话长期 >3 个且频繁冲突 → 上锁或把 `05` 拆成按线分片。
- 纯文本 diff 已经看不出改动意图 → 引入 changelog 结构化字段。
