# 存量项目改造手册

> 给「已经有一堆文档、多个会话在跑、上下文容易满」的老项目用。
> 从零搭新库走 `kb-init.py`（SKILL.md §2），**不要**用本手册。
> 配套话术：`assets/migration-prompt.txt`（可直接复制给新会话）。
>
> **已经按 v1 建好库、只想升到 v2（补 schema 标记与稳定章节 ID）** → 直接跳 §8，
> 一条 `kb-migrate.py` 命令，别重跑本手册的五步。

## 0. 先判断该不该改

| 信号 | 判断 |
|---|---|
| 接手要「全读 N 份文档」才能干活 | 改 |
| 全库 > 100 KB，而接手真正需要的信息 < 20 KB | 改 |
| 「现在在干嘛 / 待办」散在 3 处以上，且互相矛盾 | 改 |
| 两个以上会话并行，共享文档被后写者覆盖过 | 改（**先做步骤 1**） |
| 只有一条线、文档 < 30 行、只有一个会话、一次性任务 | **别改**，加了层反而要翻两份 |
| 只是要把当前会话交给下一个会话（要一份 handoff / 继续提示词） | **别改**，用 `SKILL.md`「适用边界」里的 6 行简单 handoff 模板 |

改造的目标不是「文档变薄」，是 **把「存」和「读」解耦**：总字数可以涨，单次接手的必读集合恒定在三份以内。

## 1. 第 0 步：只读诊断（先别动任何文件）

```bash
S="$HOME/.skills-manager/skills/handoff-kb/scripts"
py "$S/kb-check.py" --target "[项目目录]" --loose
cd "[项目目录]" && git status --short && git log --oneline -5
find . -maxdepth 2 -type f \( -name "*.md" -o -name "*.txt" \) -printf "%s %p\n" | sort -rn | head -20
```

`--loose` 用于已有自己命名体系的项目（`60_进度.md` / `00_INDEX.md` / `HANDOFF.md` 之类）：必需文件名缺失只报 WARN，其余照跑。**别一上来就 `kb-init.py` 覆盖**，脚手架只适合空目录。

> **数据产物会污染体积统计**：解包 / 采集 / 构建目录下的 `.md`、`.txt`（以及 >2 MB 的文本）不是交接文档。`kb-check.py` 已自动跳过 `AI_files/` / `assets/` / `data/` / `output/` / `evidence/` / `paktools/` / `node_modules/` / `build/` / `dist/` / `vendor/` / `tmp/` 和 >2 MB 文件，体积表会打印「已跳过 N 个数据产物」。实测某游戏项目跳过 268 个后，全库从 400 MB 回到 454 KB，接手成本比例（7.5%）才有意义。

从输出里读五件事，写成 3–5 行诊断结论（不用落盘）：

1. **接手成本**：现状层 + 基线占全库多少（>25% 说明必读集合太大）。
2. **有没有 git**：没有 → 步骤 1 是 P0，后面任何拆分都无法回滚。
3. **明文凭证**：有 → 立刻处理，绝不进历史。
4. **编号契约**：有没有已在跨文档引用的 `K-xx` / `G-xxx` / `§` 编号（有就绝不能重排）。
5. **未提交改动**：有 → 别的会话正在写，动笔前先看清，别替别人 commit。

## 2. 五步 SOP（别跳步，别提前拆）

### 步骤 1 · `git init`（P0，先 `.gitignore` 再 `add`）

**目标**：让后面每一步都能 diff、回滚、看见别人改了什么。

```bash
cd "[项目目录]"
cat > .gitignore <<'EOF'
.workbuddy/
*.log
logs/
*.mp4
*.part
归档/_backup_*/
scripts/_tmp_*
*.bak
Thumbs.db
EOF
git init -b main
git config user.name "你的名字" && git config user.email "you@example.com"   # 已有全局身份可跳过
git config core.autocrlf false && git config core.quotepath false
printf '* text=auto eol=lf\n' > .gitattributes
git add -A && git commit -m "初始基线：改造前原样快照"
git ls-files | grep -Ei '\.(mp4|zip|log)$' && echo "!! 有大文件进库" || echo "OK：无大文件"
```

**判据**：`git status` 干净、仓库 < 10 MB、`git ls-files` 里没有视频/日志/凭证。
**坑**：
- 大二进制进了历史就删不掉，只能 `filter-repo` 重写历史 —— 所以 `.gitignore` 必须写在**第一次 `git add` 之前**。
- 成品交付物（xlsx 等）要进库以便回滚，但 diff 看不出内容 → 在 commit message 里写「版本号 + SHA256」。
- Windows 上 `core.autocrlf=false` + `.gitattributes` 必设，否则每次 checkout 都产生整文件 CRLF 差异。
- 明文凭证：先改成环境变量 / 移到不入库的记忆目录，再 add。`kb-check.py` 会扫 `LTAI` / 私钥 PEM / `password=` / `sk-`。

### 步骤 2 · 过程下沉到 `90`

**目标**：主文档只留「当前值 / 不变量 / 判据 / 命令 / 踩过的坑与结论」。

| 该搬走（过程） | 该留下（资产） |
|---|---|
| 已结案的历史矛盾、翻案过程 | 当前基线与配置值 |
| 验证快照、一次性复核记录 | 判据与核实方式（命令） |
| 版本考古、构建 run / release 编号流水 | **踩过的坑与结论** |
| 一长串「11-06 11:32 补了…」时间戳 | 策略与不变量 |
| 已消除的矛盾、被取代的旧口径 | 常用命令参考 |
| 一次性任务单、拆分前备份 | 编号契约（§ / K-xx） |

做法：按主题在 `90_过程档案.md` 开 `§A`–`§G`（或 `归档/` 分卷），**整段原样搬**，主文档对应位置只留 `详见 90 §X`。

```bash
# 整行原文搬运 + 字节校验，别手抄
sed -n '70p' 05_进度仪表盘.md >> 90_过程档案.md
sed -n '70p' 05_进度仪表盘.md > /tmp/l70.txt
tail -n 1 90_过程档案.md > /tmp/l90.txt
cmp /tmp/l70.txt /tmp/l90.txt && echo IDENTICAL
```

**坑**：删过程时最容易连「坑与结论」一起删掉，下次重走旧路。搬完 `grep -rn "详见 90"` 确认指针都在，`kb-check.py` 的「残留 TODO / 明文凭证」应为 0。

### 步骤 3 · 建 `05_进度仪表盘.md`

**目标**：全库唯一的状态同步点，读一份就接上所有线。

从这些地方把「状态 / 待办 / 进度」抽出来：各文档末尾的待办表、`新会话启动话术.txt`、`README` 的「当前进度」、issue/任务清单、会话摘要。

结构固定（§0–§6）：`§0 现状 ≤4 行` / `§1 各线状态` / `§2 待办·待定·进行中` / `§3 交叉点` / `§4 接手顺序` / `§5 维护规则与阈值` / `§6 最近 5 条摘要（单条 ≤3 行）`。

```bash
# 删同源副本：同一个状态在多处出现就是漂移源
grep -rn "现在在做什么\|当前进度\|待办" --include="*.md" --include="*.txt" .
```

**已完成的事从 §2 移走**，写进 `06`；别让待办区被历史稀释。
**验收**：只看 `05` 一份，答得出四问（见 §3 本手册末尾）。答不出 = 缺信息或又膨胀了，别靠全读全库去补。

### 步骤 4 · 拆 `06`（触线才拆）

**触线判据**（满足任一）：`05` 出现单条 > 3 行、或 `05` 涨到 ~70 行 / 17 KB、或「接手读 05 等于在读日志」。
**别提前拆**：进度文件只有 30 行时拆两份，反而要翻两份。

两种形态，按并发程度选：

| 形态 | 适用 | 做法 |
|---|---|---|
| 单卷 `06_会话日志.md` | 单会话 / 低并发 | append-only，超 200 行 / 60 KB 按主题折叠进 `90` |
| **按线分片** `06_流水/<线>.md` | 多会话并行（**推荐**） | 一写者一文件，从根上不共享单文件；`06_会话日志.md` 转历史卷只读 |

分片命名按项目的「线」（固件 / 运行态 / 服务端 / 测速 / 文档线 / 其他），`其他.md` 收跨线交叉点。每片头部写死「只写本线、不改别人的行、每条 1–3 行、单分片 200 行 / 60 KB 折叠」。

```bash
mkdir -p 06_流水
# 从 05 整条搬到对应分片，用 sed -n 'Np' >> + cmp 校验，别手抄
sed -n 'Np' 05_进度仪表盘.md >> 06_流水/文档线.md
```

`AGENTS.md` 写回段、`05` §5、分片头部三处同源，改一处必须同步另外两处。

### 步骤 5 · 加机制（把「靠纪律」换成「靠机制」）

| 机制 | 验收 |
|---|---|
| `AGENTS.md` 唯一入口（+ `CLAUDE.md` / `GEMINI.md` 两行指针） | 三者只写「读哪份、怎么写」，**不写当前值** |
| `00` 的 `K-xx` 编号 + 状态列（有效 / 待核 / 已作废） | 引用写 ID 不复述数值；作废行连 ID 保留、不复用 |
| `05` §5 写死阈值表（§0 ≤4 行、§6 ≤5 条、单分片 200 行 / 60 KB） | 触线才动手 |
| 收尾 `git add -A && git commit -m "<线> <做了什么>"` | `git status` 干净、每步一个 commit |
| 只读自检脚本（实机/远端核对，只 echo 不改） | 每次接手先跑 |
| 每日体检 automation（可选） | 报告写 `归档/体检/`，只存档、不进 `05`/`06`、不 commit |

> `归档/体检/` 这类每日生成目录记得加进 `.gitignore`，否则 `git status` 会常驻一个未追踪目录。

## 3. 验收

1. **四问**：只看 `05` 一份，答得出「各线状态 / 下一手 / 待定与进行中 / 动某配置该读哪几份」。
2. **体检**：`py kb-check.py --target . --strict` → 0 ERR、0 WARN。
3. **git**：`git status` 干净、`git log --oneline` 能看出五步各自的提交。
4. **接手成本**：`00`+`05` 占全库 < 15%（实测老项目改造后 8.2%）。
5. **编号**：`kb-check.py` 报「K/G 编号无重复定义」，跨文档引用 grep 得到位。

## 4. 回滚

git 是底，每一步一个 commit：

```bash
git log --oneline            # 找到要回到的那一步
git diff <commit>~1 <commit> # 看这一步改了什么
git revert <commit>          # 或 git reset --hard <commit>（仅本地、未推送时）
```

过程内容没有丢，全在 `90` / `归档/`，所以「删掉的过程」随时能查回来 —— 这是敢大幅精简主文档的前提。

## 5. 与「从零搭建」的区别

| | 从零 | 存量改造 |
|---|---|---|
| 入口 | `kb-init.py --target DIR --lines ...` | `kb-check.py --target DIR --loose` 先诊断 |
| 第一步 | 生成骨架 | `git init` + 原样快照 commit |
| 内容 | 填空模板 | **搬**已有内容，只删过程、不删结论 |
| 风险 | 低 | 编号契约、并发覆盖、凭证进历史 |
| 顺序 | 一步到位 | 五步别跳，每步 commit |

## 6. 真实案例（本项目 2026-11-08）

- 起点：5 份文档 1,262 行、接手全读 221 KB（≈49k tokens）、进度散在 4 处、无 git。
- 路径：清理过程 → 建 `90` 归档 → 建 `05` → 拆 `06` → `git init` → `AGENTS.md` 三入口 → `K-01`–`K-18` 编号与状态列 → 每日体检 automation → `kb-outline.py` 分段读 → `06_流水/` 六分片。
- 结果：全库涨到 310 KB（过程被归档而非删除），**接手只需 25 KB / 8.2%（≈5.6k tokens）**，`kb-check.py` 全绿。
- 并发实测：`git status` 多次抓到别的会话未提交的 `05`/`06` 改动，靠「只追加 + 各自 commit」避免覆盖；分片后各线 10–14 行，根除共享单文件。
- 另一项目 FFRS 用 `--loose` 直接体检（自有命名 `60_进度.md` / `00_INDEX.md`），不用先改造就拿到 5 条 WARN 判读清单。

## 7. 反模式

| 坑 | 后果 |
|---|---|
| 先 `git add` 才想起排大文件 / 凭证 | 进历史删不掉 |
| 删过程时连坑与结论一起删 | 下次重走旧路 |
| 进度文件 30 行就拆 `06` | 接手要翻两份 |
| 长话术留三份同源 | 改一处漏两处，口径漂移 |
| 重排 `§` / 复用 K-xx ID | 全库引用失效 |
| 整文件覆盖写 `05` | 抹掉别的会话刚追加的行 |
| 新会话第一眼全读全库 | 继续烧 token，改造白做 |

## 8. v1 → v2 升级（`kb-migrate.py`）

v1 的库能用，只是少了三样东西：协议版本标记、稳定章节 ID、按哈希校验的写回。补齐它们不需要重排文件、不需要改正文。

### 8.1 判定要不要升

```bash
S="$HOME/.skills-manager/skills/handoff-kb/scripts"
py "$S/kb-migrate.py" --target "[项目目录]" --plan
```

输出里看三项：`schema`（`null` = v1）、`section_ids`（`0` = 没有稳定 ID）、`fact_numbers`。

| 现状 | 结论 |
|---|---|
| `schema: 2` 且 `section_ids > 0` | 已是 v2，什么都不做（脚本自己也会跳过） |
| `schema: null` | v1，建议升 |
| 事实分册是 `01`–`04` | **正常**，v2 兼容，不要求改成 `10`–`17`（见 8.3） |
| 事实分册 > 8 个 | 先按 §2 步骤 4 合并分片，再迁移 |

### 8.2 升级动作（只做三类增量）

| 动作 | 具体行为 |
|---|---|
| 补协议版本 | 在 `00` / `05` 首行插入 `<!-- kb:schema: 2 -->` |
| 补章节 ID | 按标题关键词给已知章节加 `<!-- kb:id: ... -->`，**已有 ID 的跳过** |
| 其余 | **不动**。不重命名文件、不改编号、不删任何行、不碰正文 |

映射表在 `kb-migrate.py::DASHBOARD_IDS` / `BASELINE_IDS`，按关键词顺序匹配、命中即停；只给 `##` 级章节打 ID（`#` 是文档标题，不是事实章节）。

```bash
py "$S/kb-migrate.py" --target "[项目目录]" --plan    # 写 .kb-migrate-plan.json
py "$S/kb-migrate.py" --target "[项目目录]" --apply   # 校验哈希后执行
```

- 计划文件绑定源文件 SHA-256：`--apply` 时先校验，**文件被别的会话改过就拒绝执行（退出码 1）**，绝不覆盖。
- 有未提交改动时默认拒绝迁移；确认那些改动无关才加 `--force`。
- 幂等：连跑两次，第二次报告「无需迁移」。
- 回滚：`git checkout -- 00_*.md 05_*.md`（迁移只碰这两份，且每份都在 git 里）。

### 8.3 编号兼容（最容易误判的一条）

v2 的新事实分片用 **`10`–`17`**，`00` / `05` / `06` / `90` 是保留号；**旧的 `01`–`04` 事实分册继续有效**，`kb-check.py` 不会报错，`kb-context.py` 照常读。

为什么不是「全部改成 10–17」：老库里的 `§` 编号、`K-xx` 引用、别的会话的待办、外部链接都指着旧文件名。为了一次性的整齐去重排，代价是全库引用失效——这正是 §7 最后几条反模式的根源。**新老混用是设计上的兼容，不是历史包袱。**

### 8.4 升级后验收

```bash
py "$S/kb-check.py" --target "[项目目录]"      # 应 0 ERR
py "$S/kb-outline.py" --target "[项目目录]"    # 应看到 kb:id 列表
py "$S/kb-context.py" --target "[项目目录]" --task "查看当前项目状态"
```

第三行能返回 `dashboard.current` 而不是空，就说明路由链路通了。
