# Token 与接手质量评测口径

> `scripts/kb-benchmark.py` 的说明书。回答三个问题：
> 省了多少 token、省得对不对、这个数字能不能拿去对外说。

## 0. 一句话

固定 10 个任务，同一份库，比三种读法的**上下文体积**与**答对率**：

| 读法 | 含义 | 对应现实 |
|---|---|---|
| **A 全量** | 库里所有参与检索的文本 | 「新会话先把文档全读一遍」 |
| **B 旧法** | 只读 `00` + `05` | 本技能 v1 的推荐读法 |
| **C 新版** | `kb-context.py` 按预算路由 | v2 的推荐读法 |

C 的合格线不是「越小越好」，是 **C 小且质量不掉**。压缩比再漂亮，硬约束丢了就是负收益。

## 1. 复现

```bash
S="$HOME/.skills-manager/skills/handoff-kb/scripts"
py "$S/kb-benchmark.py" --target "[项目目录]" --report markdown
py "$S/kb-benchmark.py" --target "[项目目录]" --report json --budget 3000
```

- 依赖：无。不联网、不装包、不调模型。
- `--budget`：传给 `kb-context.py` 的预算（默认 3000）。
- `--report json`：给 CI / 二次统计用，字段见 §5。
- 退出码：质量通过 ≥8/10 → `0`，否则 `1`；目标不是交接库 → `2`。

## 2. 实测输出（本仓库测试夹具，可复现）

夹具由 `tests/common.py::make_filled()` 生成：2 条工作线、4 条事实（含 1 条已作废、1 条待核）、1 条流水。

```bash
py tests/make_fixture.py ../kbdemo
py scripts/kb-benchmark.py --target ../kbdemo --report markdown
```

## 3. 怎么读这些数

**C 不是恒小于 B。** 任务 6/7 的 C 比 B 大（199 / 194 vs 389 是整库 00+05，仍小于 B，但明显高于其它任务），原因合理：问「哪些配置已作废 / 哪些结论待核」必须把事实表整段拿出来逐行判断，只给一条 `K-03` 反而答不了。**该给整表的时候给整表**，这是质量优先于压缩的显式取舍。

**P4 噪声比 = P4（补充材料）token / 本次上下文 token。** 0 表示这次只读了 P0–P2；0.45–0.52 表示一半上下文是「可能有帮助但不确定」的补充块。判读：

| 噪声比 | 判读 |
|---|---|
| 0.00–0.30 | 正常，路由精确 |
| 0.30–0.60 | 可接受：任务本身是「全表判断」类（作废 / 待核 / 交叉） |
| > 0.60 | 该查词典了：多半是 `lib/terms.py` 把任务切成了过泛的二字词 |

噪声比是**诊断量**，不是及格线——不参与 pass/fail。因为「为了低噪声而漏掉该读的表」比「多读 200 token」更贵。

**质量项逐条怎么判**（`kb-benchmark.py::main`）：

| 任务类型 | 通过条件 |
|---|---|
| `section_id` | 期望的 `kb:id` 出现在返回块里，**且** P0 硬约束块存在 |
| `gap_or_hit` | 期望词出现在上下文、缺口列表、或 P0 块中 |
| `gap` | 返回了非空 `gaps`，且 P0 块存在 |
| `exit2` | 错误路径被拒绝（退出码 2） |

硬约束（P0）是四个判据里唯一**每个任务都要求**的项——这是「省 token 不省安全边际」的机械保证。

## 4. Token 数是怎么来的

| tokenizer | 精度 | 什么时候用 |
|---|---|---|
| `heuristic`（默认） | 估算：CJK 1 字 ≈ 1 token，其余 4 字符 ≈ 1 token | 日常、CI、跨机器可比 |
| `tiktoken`（可选） | 真实 BPE 计数 | 要对外报数、要跟账单对账 |

装了 `tiktoken` 才可用第二种，**不装也能跑**：缺包时自动降级为启发式，并把 `tokenizer` 字段写成
`heuristic（未找到 tokenizer 'xxx'，已降级估算）`——降级是显式的，不是静默。本技能不装任何依赖，
`tests/deps_check.py` 保证 `scripts/` 里只出现标准库与本地 `lib`，`tiktoken` 是唯一例外且必须在函数内
`try/except`。报告里 `tokenizer` 一行永远是实际生效的那个，看到 `heuristic` 就别把数字当账单。

## 5. JSON 字段

```json
{
  "target": "...", "budget": 3000, "tokenizer": "heuristic…",
  "tokens": {"A_all": 3055, "B_00_05": 389, "C_mean": 89.0},
  "reduction_vs_B": 0.771,
  "quality": {"passed": 10, "total": 10, "rate": 1.0},
  "rows": [{"id": 1, "title": "...", "a": 3055, "b": 389, "c": 38,
            "noise": 0.0, "quality": "命中 dashboard.current",
            "pass": true, "ms": 115}],
  "notes": ["..."]
}
```

`ms` 是单次 `kb-context.py` 的进程启动 + 计算耗时，含解释器启动，**不是**算法复杂度指标。

## 6. 真实项目 vs 夹具：别混着说

| 来源 | 可以说什么 | 不可以说什么 |
|---|---|---|
| 夹具（`make_filled`） | 三种读法的比例、质量项全过、错误路径被拒 | 「省了 77% token」当成产品指标 |
| 真实项目（自己的库） | 「我这个库，接手从 X token 降到 Y token，任务集是这 10 个」 | 推广成「所有项目都省 Y%」 |

真实项目跑法一样，只是 `--target` 换成自己的目录。任务集是**固定的通用 10 条**，不含你项目特有的问题，所以真实项目的 C 通常比夹具大（库更大、命中更散），降幅通常比夹具小——这是正常的，不是回归。

一条已有的真实观测（FFRS，自有命名体系，非标准 v2 库）：全库约 310 KB、接手必读约 25 KB（8.2%），`kb-check.py --loose` 直接可用。这类数字写进 README 时必须带项目名和日期，不能抽象成普适结论。

## 7. 这个评测测不到什么

- **答得对不对**：只测「该读的段落有没有进上下文」，不测模型读完之后的推理质量。
- **多轮对话**：单轮任务，不含追问、纠错、上下文累积。
- **写回质量**：`kb-write.py` 的正确性由 `tests/test_write.py` 覆盖，不在这里。
- **延迟/成本**：`ms` 含进程启动；真实 API 的延迟与计费跟 token 数不是线性关系。
- **极端库**：>10 MB 或 >500 文件的库没做过压力测试；`kb-context.py` 有 P4 上限兜底，但检索仍是全库扫描。

## 8. 改动这个脚本时

- 任务集是**契约**：加减任务要同步改 §2 的表和 README 里的数字，否则文档就开始撒谎。
- 判据别放宽：`section_id` 类任务必须同时验 P0，否则「把硬约束裁掉换低 token」能刷分。
- 别为了让降幅好看去调 `--budget`；预算该由「接手方模型的上下文窗口」决定，不由评测决定。
- 新增指标先想清楚它是 pass/fail 还是诊断量；诊断量混进及格线会让脚本变成调参游戏。
