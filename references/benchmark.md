# Token 与接手质量评测口径

> `scripts/kb-benchmark.py` 的说明书。回答三个问题：
> 省了多少 token、省得对不对、这个数字能不能拿去对外说。

## 0. 一句话

固定 10 个任务，同一份库，比三种读法的**上下文体积**与**答对率**：

| 读法 | 含义 | 对应现实 |
|---|---|---|
| **A 全量** | 库里所有参与检索的文本（含子目录，排除资料目录与 >2 MB 文件） | 「新会话先把文档全读一遍」 |
| **B 旧法** | 只读 `00` + `05` | 本技能 v1 的推荐读法 |
| **C 新版** | `kb-context.py` 按预算路由 | v2 的推荐读法 |

C 的合格线不是「越小越好」，是 **C 小且质量不掉**。压缩比再漂亮，硬约束丢了就是负收益。

**主看 C 相对 A。** A 才是「全读」的真实成本。相对 B 在小库上会为负——因为 C 含包装
（`## [P0]` 标题、`<!-- source -->`、选择理由、缺口、指针），B 只是 `00+05` 原文。
拿「C 比 B 小多少」当卖点，在小库上必然翻车。

## 1. 复现

```bash
S="$HOME/.skills-manager/skills/handoff-kb/scripts"
py "$S/kb-benchmark.py" --target "[项目目录]" --report markdown
py "$S/kb-benchmark.py" --target "[项目目录]" --report json --budget 3000 --loose
```

- 依赖：无。不联网、不装包、不调模型。
- `--budget`：传给 `kb-context.py` 的预算（默认 3000）。
- `--loose`：自有命名项目（`60_进度.md` / `61_流水.md` / `60_流水/`）必须加。
- `--report json`：给 CI / 二次统计用，字段见 §5。
- 退出码：过质量门 → `0`；未过 → `1`；目标不是交接库 → `2`。

## 3. 10 项质量指标：5 项硬门槛 + 5 项仅报告

指标分两级，因为把「受夹具内容限制的指标」写死成 100% 只是把测试调绿，不是质量提高。

**必须 100%（任一不达标，退出码 1）**

| 指标 | 通过条件 |
|---|---|
| 硬约束保留 | 每条任务都有 P0 块（`dashboard.constraints` 或 `AGENTS.md` 硬约束段） |
| 错误路径被拒绝 | 不存在的目录 → 退出码 2 且 stderr 有 `ERR` |
| 预算如实 | `used ≤ budget`，且 `over_budget` 与实际一致（不谎报） |
| 工作线无静默遗漏 | `selected_lines` 与 `omitted_lines` 不交叉；省略的线在缺口里有说明 |
| 计数器口径一致 | `requested` 与传入的 tokenizer 一致，`exact` 与实际能力一致 |

**仅报告（记录数值，不拦合并）**

| 指标 | 通过条件 |
|---|---|
| 目标章节命中 | `section_id` 类任务的期望 `kb:id` 出现在返回块里 |
| 目标事实命中 | 按 ID 问事实时，返回块里含该 ID 且状态判定正确 |
| 缺口如实报告 | `gap` / `gap_or_hit` 类任务真的返回了非空 `gaps` |
| 归档未混入默认上下文 | 块的 `source` 不含根层归档角色的文件（`90_*.md` / `*归档*.md`） |
| P4 受数量与预算约束 | P4 块数 ≤3、P4 token ≤ 预算 30%、噪声比不被静默忽略 |

质量门（同时满足才退出 0）：

1. 可评任务通过数 ≥ 80%（**向上取整**，10 个任务即 ≥8，8 个任务即 ≥7）；
   不要用 `round()`/`四舍五入`：`round(8*0.8)=6` 只有 75%，门槛会名不副实；
   也尽量不用 `math.ceil(total*0.8)`：0.8 在二进制里不精确，任务数一变就要讨论
   「差一点点算不算进位」。实现用整数运算 `(total*4 + 4) // 5`，不引入浮点。
2. 10 项指标总通过率 ≥ 80%；
3. **5 项硬门槛满通过**。

第 3 条是为了防「平均值掩盖致命退化」：少一条硬约束、放过一个坏路径，不该被 90% 的漂亮均值盖住。

**工作线召回**单独报三档：`完整`（该加载的线都进了上下文）/ `部分`（进了但有省略且已说明）/ `静默`（漏了且没说）。静默遗漏计入硬门槛的失败。

**可评任务**：库还没有任何 `kb:id`（v1，未迁移）时，`section_id` 类任务无法验证，
标成「跳过：未迁移库没有 kb:id」，不进通过率分母，并在报告末尾提示先跑 `kb-migrate.py`。
同理，库里没有「已作废」事实时，「作废要指向替代」这条也标跳进——那是没有可测对象，
不是答对。这不是放水，是不让「没测到」冒充「通过了」。

## 4. Token 数是怎么来的

| tokenizer | 精度 | 什么时候用 |
|---|---|---|
| `heuristic`（默认） | 估算：CJK 1 字 ≈ 1 token，其余 4 字符 ≈ 1 token | 日常、CI、跨机器可比 |
| `tiktoken`（可选） | 真实 BPE 计数 | 要对外报数、要跟账单对账 |

A / B / C **用同一个 `TokenCounter` 实例**：A、B 是 `counter.count(text)`，C 取
`kb-context.py` 的 `used`（它内部也是同一个计数器），子进程通过 `--tokenizer` 对齐。
早先 A/B 走 `estimate()`、C 走另一条路，数字对不上，已经改掉。

缺 `tiktoken` 时**不会静默降级**：指定了 `--tokenizer cl100k_base` 却装不上编码器，
`kb-context.py` 直接退出 2，要求你显式加 `--allow-tokenizer-fallback`（报告里 `exact: false`）。
`tests/deps_check.py` 保证 `scripts/` 只出现标准库与本地 `lib`，`tiktoken` 是唯一例外且必须在函数内 `try/except`。

## 5. JSON 字段

```json
{
  "target": "...", "budget": 3000, "tokenizer": "heuristic…",
  "exact": false, "loose": false, "unmigrated": false,
  "tokens": {"A_all": 3082, "B_00_05": 389, "C_mean": 454.3, "C_error_paths": 1},
  "reduction_vs_A": 0.853,
  "reduction_vs_B": -0.168,
  "quality": {"passed": 10, "total": 10, "rate": 1.0},
  "metrics": {"constraint_kept": {"label": "硬约束保留", "passed": 9, "total": 9},
              "p4_bounded": {"label": "P4 受数量与预算约束", "passed": 9, "total": 9}},
  "metrics_rate": 1.0,
  "recall": {"full": 1, "partial": 0, "silent": 0},
  "gate": {"min_rate": 0.8, "min_passes": 8,
           "must_pass": ["constraint_kept", "error_rejected", "budget_honest",
                         "lines_honest", "tokenizer_consistent"],
           "hard_ok": true, "passed": true},
  "rows": [{"id": 1, "title": "...", "a": 3082, "b": 389, "c": 329,
            "noise": 0.0, "counted": true, "graded": true,
            "quality": "命中 dashboard.current", "pass": true, "ms": 164}],
  "files": [{"path": "00_基线.md", "tokens": 98}],
  "notes": ["..."]
}
```

- `counted`：参与 C 均值。错误路径为 `false`。
- `graded`：参与通过率。未迁移库的章节类任务、或库里没有对应状态事实的任务为 `false`。
- `metrics` 里的键是稳定的；`gate.must_pass` 列出这一版必须 100% 的 5 项，**别把 `metrics_rate` 单独当结论**。
- `recall`：多工作线召回的完整 / 部分 / 静默计数；`silent > 0` 一定伴随 `gate.passed = false`。
- `ms` 是单次 `kb-context.py` 的进程启动 + 计算耗时，含解释器启动，**不是**算法复杂度指标。

## 6. 三种数据源：别混着说

| 合成夹具（`make_fixture`） | 三种读法的比例、10 项指标全过、错误路径被拒 | 「省了 85% token」当成产品指标 |

这正是评测该做的事：**它没有把「省了 99.9%」当成功**，而是指出「这个库没有任何地方声明硬约束，
按章节路由也测不了（0 个 `kb:id`），36 条事实一条都没标状态（有效 0 / 待核 0 / 作废 0 / 未知 36）」。
修法是补约束段、给事实补状态、跑 `kb-migrate.py --plan`，不是调参。

同一库里 `kb-check --loose` 的编号检查从 **ERR 4 → ERR 0**：`00_INDEX.md` 的「待核」列表里有
4 条 `- G-0xx：…` 导航行，和分册的正式定义撞了；现在按索引页指针处理（判定规则见 SKILL.md §8），
并用 `kb-context --task "G-011 现在还算数吗"` 验证 P3 块来源从索引页变成 `10_游戏事实.md`。

### 6.1 撤回：2.0 文档里的「C = 89 tokens / 降 77%」与 2.0.1 的「C = 395.6」

- **89 tokens**：产生于 `kb-context.build()` 根本没把 P2 放进装配队列的缺陷版本——少给内容所以数字小，被写成「很省」。
- **395.6 / 1,886**：任务集从「查找某项事实 / 追踪证据 / 冲突知识判断」换成「按 ID 定位事实 / 作废指向替代 / 待核标待核」，指标从 8 项变 10 项，口径变了，这组数不再可比，**已从 README 与本文件删除**。

判断依据很简单：`used` 只有 89，而 P0+P1 本身的包装就超过这个量。现在的实现会
1) 先把 P2 真正装配进去，2) 按**最终渲染**收敛预算，3) 把装不下的线写进 `omitted_lines` 与缺口。
宁可数字变大，也不把「漏给」记成「省了」。

### 6.2 2.0.1 → 2.0.2 三库对照（只读，同一任务集）

同一批任务、同一预算（3000）、同一 tokenizer 口径，两个版本各跑一遍
（2.0.1 = `main` 的 `b524c56`；2.0.2 = `fix/2.0.2-gate-summary`）。
三个库都在 `H:\AI工作区` 下，只读，没改任何文件。

| 库 | 任务数 | 2.0.1 `used` 合计 | 2.0.2 `used` 合计 | 变化 |
|---|---|---|---|---|
| 求职261104 | 4 | 5,242 | 4,925 | −317（−6.0%） |
| 路由器和网络 | 6 | 16,101 | 15,888 | −213（−1.3%） |
| FFRS | 5 | 7,976 | 8,737 | **+761（+9.5%）** |

FFRS 变贵，是因为**装进去的内容换了**，不是包装变胖：

| 任务 | P4 换掉了什么 | P4 换成了什么 |
|---|---|---|
| 机械冲撞伤害怎么算 | `.shared/memory/2026-11-12.md`（知识库改造日志） | `10_游戏事实.md` 的 G-001 / G-017 / 常见误判（3 节） |
| 幻兵培养表怎么更新 | `.shared/memory/2026-11-12.md` | `10_游戏事实.md` 的 G-010 |
| 解包数据在哪里 | `.shared/memory/2026-11-08.md` | `20_数据与解包.md` D-011 + `30_mod开发.md` M-008 |
| 磁盘写满怎么办（路由库） | `.workbuddy/memory/2026-11-07.md` | `xray-hy_磁盘写满事故报告_20261107.md` |

同时 `gaps` 少了 2 条/任务（P0 假缺口撤回），P4 缺口改成边界说明（约 55 tokens/任务），
其余增量都来自真实分册正文。省 token 不是唯一目标：把 `.shared/memory` 里的
「某天做过什么」换成游戏事实，多花 9.5% 是正收益。

`kb-benchmark` 自身的 A/B/C 均值**不要跨版本直接比**，两处口径变了：

- **A 的语料变了**：2.0.2 起 `.workbuddy` / `.shared` 等 15 个客户端目录不算正文，
  于是路由库 A 从 281,420 降到 211,569、FFRS 从 1,756,150 降到 1,733,275。
  这是「不该算的东西不算了」，不是库变小了。
- **C 的分母变了**：FFRS 的可评任务从 8 条变 9 条——P0 假缺口修好后，原本因
  「找不到硬约束」被跳过的一条变成可评。均值分母不同，数字没有可比性，
  所以上表用的是**同一任务集的 `used` 合计**。

质量侧没有退步：三库硬门槛全过（`hard_ok: true`），质量项分别 6/6、5/5、9/9（全 100%）；
FFRS 的工作线召回从 `完整 0 / 部分 0 / 静默 0` 变成 `0 / 1 / 0`——终于有一条任务
被判成「部分召回且已说明」，而不是「什么都没召回还不吭声」。

## 7. 这个评测测不到什么

- **答得对不对**：只测「该读的段落有没有进上下文」，不测模型读完之后的推理质量。
- **多轮对话**：单轮任务，不含追问、纠错、上下文累积。
- **写回质量**：`kb-write.py` 的正确性由 `tests/test_write.py` / `test_transaction.py` 覆盖，不在这里。
- **延迟/成本**：`ms` 含进程启动；真实 API 的延迟与计费跟 token 数不是线性关系。
- **极端库**：>10 MB 或 >500 文件的库没做过压力测试；`kb-context.py` 有 P4 上限兜底，但检索仍是全库扫描。

## 8. 改动这个脚本时

- 任务集是**契约**：加减任务要同步改 §2 的表和 README 里的数字，否则文档就开始撒谎。
- 判据别放宽：`section_id` 类任务必须同时验 P0，否则「把硬约束裁掉换低 token」能刷分。
- 别为了让降幅好看去调 `--budget`；预算该由「接手方模型的上下文窗口」决定，不由评测决定。
- 新增指标先想清楚它是 pass/fail 还是诊断量；诊断量混进及格线会让脚本变成调参游戏。
- 归档类指标的比对基准只能用**根层归档角色文件**：块的 `source` 是文件名，用「归档目录下全部文件名」
  去比对，遇到「`归档/` 里存了一份整库备份」就会撞名误报（真实 FFRS 上曾误报 5/9）。
